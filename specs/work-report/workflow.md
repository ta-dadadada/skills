# work-report 整備記録

対象: `dev/work-report`。作成済みスキルを、ユーザー指定の shiranui-hanten（個人用に配置された版）の Step 0–7 に従って更新する。リポジトリ内の旧版ではなく、会話で指定された本文と参照仕様を適用する。

## Step 0 — 更新経路と診断

対象の SKILL.md 全文、APM 定義、ルートの配布一覧を確認した。対象スキルに外部参照ファイルはない。

- Unclear boundary: description はセッション外変更の確認を明示期間の説明に含める一方、本文は期間未指定でも確認を求める。起動時にも共通の確認境界が読めるようにする。
- Unclear boundary: セッション限定時の「含めるか」という質問は期間拡張を暗黙に招く。既定の期間を維持し、拡張はユーザーの明示指示に限ることを記述する。
- Premature completion: 対象範囲を定める工程の完了条件を追加し、証拠収集の範囲を固定する。
- 本文は既に標準構成を持つ。全体の書き直しや別スキルへの分割を必要とする証拠はない。
- 未検証範囲: 実環境の過去セッション検索・メモリ取得、複数モデル間の挙動、利用者による実運用。以前の架空ケースは実履歴取得の証拠と扱わない。

完了: 更新経路、根拠のある指摘、未検証範囲を記録した。

## Step 1 — 要件

仕事: 実行エージェントが、指定期間（未指定なら起動セッション）の根拠ある作業内容を、プロジェクト外でも理解できる簡潔な Markdown レポートにする。

主責務: procedure。期間確定、根拠確認、編集、提出の報告手順。確認境界はこの手順の品質・権限要件であり、独立起動の必要がないため分割しない。

| 種類 | 要件 |
| --- | --- |
| 必須成果 | 対象期間を明記した Markdown。未指定ならセッション内。指定時はセッション外の差分・利用可能なメモリも確認する。 |
| 品質 | 簡潔で要点中心。プロジェクト外で意味が通じる。相対ファイルリンクに依存しない。事実・予定・未完了・検証済みを区別する。 |
| 権限 | 発見したセッション外変更はユーザーに確認する。既存の明示回答は再利用する。報告依頼から公開・送信の権限を推論しない。 |
| 必須順序 | 期間確定→根拠と帰属確認→必要な回答の取得→最終レポート。回答待ちの間の確定部分の整理は可能。 |
| 推奨手段 | 概要と3–6項目、任意の検証・残件欄。Git 以外では同等の資料を使う。 |
| 許容判断 | 文量・見出し・資料の絞り込み。重大な期間境界や帰属を根拠なく決定しない。 |

スキル完了条件: 範囲と必要な確認が解決し、各記載が期間内の根拠に対応し、欠落を明示した自立的な Markdown を提出する。部分報告は明示要求がある場合に範囲を限定して提出する。

完了: 仕事、責務、完了条件、要求と裁量の区別を記録した。

## Step 2 — 起動と description

model-invoked を選択する。ユーザーがスキル名を覚えず「今日の作業を報告して」と依頼した場合にも選択される必要があるため。自発的な定期報告を意味しない。標準 frontmatter を使い、ツール固有の起動設定は追加しない。

description は期間未指定／指定の二経路、共通のセッション外確認、Markdown・簡潔さ・外部読者、引継ぎ・PR・実作業の除外を表す。本文との対応は Step 6 で検証する。

完了: 起動方式と理由、description の変更方針を確定した。

## Step 3 — 構造

| 内容 | 唯一の配置先 | 理由 |
| --- | --- | --- |
| 責務と全体完了条件 | 冒頭の thesis | 両経路に共通 |
| 起動・除外 | When to use / When not to use | ルーティングに必要 |
| 期間の分岐と範囲確定 | Workflow 1 | 収集の前提。短い分岐なので本文内 |
| 根拠、帰属、ユーザー確認、欠落 | Workflow 2 | 両経路が必要に応じて到達する共通境界 |
| 表現・長さ・出力先 | Workflow 3 | 共通の出力要件 |
| 任意テンプレート | Workflow 3 内の参照ブロック | 短い補助資料。規範を複製しない |
| 最終点検と提出 | Workflow 4 | 完了ゲート |
| 誤りの兆候 | Red flags | 診断用の短い要約 |
| 隣接責務 | Related | 別スキルの名前のみ |

条件付きの長大な資料はないため references は追加しない。独立責務や解消しない順序問題の証拠もないため分割しない。この工程記録はスキル利用時に不要なので specs に置く。

完了: 執筆前に内容の配置先と分割判断を確定した。

## Step 4 — 執筆

description の確認規則を両経路に適用し、Workflow 1 に範囲確定ゲート、Workflow 2 に期間を暗黙拡張しない規則を追加した。既存の責務、Markdown、簡潔さ、外部読者、確認待ち、欠落表示、配布方式は維持した。APM description も同期した。

完了: 指定の本文パターン、全体と判断ゲートの完了条件、標準 frontmatter を確認した。対象に外部ファイル・節へのリンクはなく、関連スキルは任意の名前参照である。

## Step 5 — 整理と秘密情報確認

本文・APM 定義を通読し、旧ルールの残存と重複を確認した。description と本文、Red flags の短い再掲はそれぞれ起動・実行・診断の役割が異なるため維持した。成果物の長さを制限する要件とスキル本文の長さを混同せず、確認や証拠の要件は削除していない。今回、観測に基づかない補償指示の追加や別スキル化はしなかった。

秘密情報確認: 配布対象の SKILL.md と apm.yml に認証情報、トークン、内部エンドポイント、ローカル個人情報はない。テンプレートは抽象的なプレースホルダーのみ。工程記録にも秘密値は記載していない。

完了: 必須保証を維持し、不要な追加資料は作成せず、秘密情報なしを目視確認した。
