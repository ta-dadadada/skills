# プロジェクトガイド

このリポジトリは、AIエージェントに作業の進め方を伝える、再利用可能な
Agent Skillsを配布するプロジェクトです。開発の開始、業務やUIの設計、
実装と検証、作業の引き継ぎ、スキル自体の改善を支援します。

スキルは機能を実装したアプリケーションではなく、判断基準や手順をまとめた
`SKILL.md` と、必要に応じた参照資料・スクリプトのパッケージです。
すべてのスキルを毎回使うのではなく、作業の目的と現在の段階に合わせて選びます。

インストール方法は[README](../README.md#github-からインストールする)を参照してください。
このガイドのスキル名から、正式な手順を記載した各 `SKILL.md` を開けます。

## まずどれを使うか

- 新しい開発作業の目的を残すなら `session-goal`。実装の完了条件や計画を整理するなら、続けて `issue-kickoff` を使います。
- UIを設計するなら `frontend-ui-design`。動く画面まで作るなら `frontend-ui-implementation` も使います。業務画面の情報構造から考える場合は、その前に `business-ui-design` を使います。
- 原因不明の不具合を調べるなら `hypothesis-driven-debugging`。テストのない既存コードを変更するなら `characterization-testing` で現在の動作を保護します。
- 作業途中で中断するなら `session-handover`、再開するなら `session-resume`。完成した変更をレビューに渡すなら `pr-handoff` です。

小さく直接的な変更では、専門スキルだけで十分な場合があります。
複数の完了条件やレビュー対応をまたいで実装を管理する必要があるときに、
`implementation-loop` を追加します。

### 実装・テスト・不具合調査

| スキル | 簡単な説明 | 主な出力・注意点 |
| --- | --- | --- |
| [implementation-loop](../dev/implementation-loop/SKILL.md) | 合意済みの完了条件を一つずつ実装・検証し、依存関係やレビュー指摘を含めて完了まで管理します。 | 完了条件ごとの証拠とレビュー結果。専門スキルの代わりではなく、実装サイクル全体を調整します。 |
| [backend-api-implementation](../dev/backend-api-implementation/SKILL.md) | 既存バックエンドのAPI変更で、入出力やエラーの契約を先に固め、テスト・実装・実リクエスト検証を進めます。 | 契約に沿ったAPIと検証結果。新規サービス全体の設計は対象外です。 |
| [frontend-ui-implementation](../dev/frontend-ui-implementation/SKILL.md) | レビュー済みのUI設計をHTML・ARIA・CSS・JSなどで実現し、実行中の画面を検証します。 | 動作するUIと実行時の証拠。設計が未確定なら `frontend-ui-design` を先に使います。 |
| [terraform-implementation](../dev/terraform-implementation/SKILL.md) | 既存Terraformコードの変更で、作成・更新・置換・削除の影響を予測し、実装と静的検証を行います。 | コード差分とリソース操作の予測。`terraform plan` は明示された場合だけ実行し、`apply` などの運用は対象外です。 |
| [characterization-testing](../dev/characterization-testing/SKILL.md) | テストがない、または信頼できない既存コードの現在の動作をテストで固定し、変更の安全網を作ります。 | 現状を記録するテスト。意外な動作やバグもまず記録・報告し、無断では修正しません。 |
| [hypothesis-driven-debugging](../dev/hypothesis-driven-debugging/SKILL.md) | 原因不明の不具合を再現し、仮説を観測で検証して原因を絞り、修正後に再現確認と回帰テストを行います。 | 根拠のある原因説明と、依頼範囲に応じた修正・検証。原因が判明済みの変更や緊急復旧は対象外です。 |

| [pr-handoff](../dev/pr-handoff/SKILL.md) | 既存差分と設計判断、検証結果から、PR説明文と論理的なコミット分割案を提案します。 | レビューに渡す説明とコミット案。stage・commit・push・PR作成は実行しません。 |

| --- | --- | --- |
| [shiranui-hanten](../meta/shiranui-hanten/SKILL.md) | スキルの新規作成・更新を、要件、発動条件、構造、執筆、整理、検証、配置の順に進めます。 | 検証済みのスキルパッケージ。このリポジトリでスキルを作成・改訂するときの基本手順です。 |
| [shiranui-hansode](../meta/shiranui-hansode/SKILL.md) | エージェント指示の構造レビュー、変更前後の実行比較、反復調整を行います。 | 指定された評価範囲の証拠と判断。明示的に評価を依頼した場合に使い、毎回の編集後には自動実行しません。 |
| [skill-opportunity-review](../meta/skill-opportunity-review/SKILL.md) | 完了した作業の学びを振り返り、既存スキル改善、新規スキル候補、文書・メモ、提案なしに分類します。 | 根拠付きの提案のみ。ファイルは作成・変更せず、通常の作業で毎回行うものではありません。 |
| [just-do-it](../meta/just-do-it/SKILL.md) | 任意の追加スキルや手続きの負担を抑え、依頼された成果物の完成まで直接進めます。 | 検証済みの成果物。明示指定した場合だけ使い、必須の規則・検証・権限の境界は維持します。 |

## おすすめの使い方

### 成果物と範囲を一緒に伝える

スキル名に加えて「何を」「どこまで」「何をしないか」を伝えると、
設計だけの依頼と実装までの依頼を区別できます。次のように依頼します。

```text
frontend-ui-designを使って、検索フォームの画面構造と操作を設計してください。
エラー表示とキーボード操作も含めてください。コードの変更はまだ不要です。
```

```text
backend-api-implementationを使って、既存APIにページングを追加してください。
既存クライアントとの互換性を保ち、テストと実リクエストで検証してください。
```

```text
hypothesis-driven-debuggingを使って、失敗するテストの原因を調べてください。
今回は原因の説明までにとどめ、修正は行わないでください。
```

呼び出し方法は利用するエージェントによって異なります。
このガイドでは、ツール固有のコマンドではなく依頼内容の例を示しています。

### 必要な段階だけ組み合わせる

- 目的や完了条件が合意済みなら、それを引き継ぎ、最初から決め直さないよう伝えます。
- 専門スキルが別のスキルへ引き継ぐ場合は、必要なスキルも導入します。たとえばUIの設計と実装には両方が必要です。
- スキルを切り替える際は、目的、対象範囲、設計判断、受入ケース、検証結果を引き継ぎます。
- 調査だけ、設計だけ、提案だけという制限は、後続スキルに進むときも維持します。
- スキルの利用は、公開・送信・Git操作・インフラ運用などを一括で許可するものではありません。

`just-do-it` は、任意の追加スキルを連鎖させずに直接進めたい場合の別の選択肢です。
以下のフローを一通り実行するための開始スキルではありません。

## 場面別の利用フロー

以下は組み合わせの例です。すべての段階が必須という意味ではありません。
各段階で何を残し、次に何を渡すかを意識すると、重複した調査や判断を減らせます。

### 1. 新しい機能の実装を始める

`session-goal` → `issue-kickoff` → 必要な設計・実装スキル → `doc-sync` → `pr-handoff`

1. 目的と成功時の変化を保存します。
2. 完了条件、対象外、ブランチ、検証計画を準備します。
3. 責務やルールの配置に判断が必要なら `purpose-driven-software-design`、API変更なら `backend-api-implementation` などを使います。
4. 実装で利用者向けの動作や設定が変わった場合、既存文書を照合します。
5. 完成した差分と検証結果をPR説明・コミット案にまとめます。実際のコミットやPR作成は別の依頼です。

完了条件が複数あるなど、実装サイクルの調整が必要な場合は、手順3を
`implementation-loop` で管理し、その中で専門スキルを使います。

依頼の確認が何度も往復しそうなら、`local-intake` の利用を相談し、
合意した場合に `issue-kickoff` の前で依頼概要を整理します。

### 2. 業務画面を設計し、実装する

`business-ui-design` → `frontend-ui-design` → `frontend-ui-implementation`

1. 業務上の作業とレコードを起点に、一覧・詳細・操作の情報構造を決めます。
2. 同じ設計記録と受入ケースを引き継ぎ、状態、フォーム、レスポンシブ、キーボード操作などの設計契約を確定します。
3. 契約に沿って実装し、実際のUIで操作・表示・アクセシビリティを検証します。

業務用語やルール自体が曖昧なら、その部分を先に `domain-modeling` で整理します。
業務の情報構造を決める必要のない一般的なUIは `frontend-ui-design` から始めます。
設計だけの依頼なら手順2まで、設計が確定済みなら実装から始められます。

### 3. テストのない既存コードで不具合を修正する

`characterization-testing` → `hypothesis-driven-debugging` → 修正と回帰検証

1. 保持すべき現在の動作をテストに記録し、安全網を作ります。
2. 不具合を再現し、観測に基づく仮説の検証で原因を特定します。
3. 修正を依頼されている場合に、確認された原因を最小限に修正し、元の再現手順と回帰テストで確認します。

現在の動作を記録するテストは、その動作が正しいことの保証ではありません。
意外な動作もまず報告し、意図的に変更する範囲を区別します。
信頼できるテストがある場合は、安全網作りを省いて不具合調査から入れます。

### 4. 既存Terraformコードを変更する

`issue-kickoff` → `terraform-implementation` → `doc-sync` → `pr-handoff`

対象範囲と検証計画を決め、リソースごとの作成・更新・置換・削除を予測してから
コードを変更します。`fmt`・`validate`・プロジェクトの静的検証を行い、
差分と予測を引き継ぎます。文書への影響があれば `doc-sync` で照合します。

`terraform plan` は明示的に指示された場合だけ実行します。
`apply`・`destroy`・実際のstate操作はこのフローの対象ではありません。

### 5. 作業を中断し、後で再開する

`session-handover` → 次のセッションで `session-resume` → 有効な次の作業

中断時は `.agent-session.md` に、変更の意図、確認済みの結果、未解決事項、
次の具体的な行動を残します。再開時はその記録を最新の依頼とGit差分に照合し、
現在も有効な次の行動から進めます。

完成した変更をレビューに渡すなら `pr-handoff`、今回の成果や指定期間の作業を
報告するだけなら `work-report` を使います。3つは目的が異なります。

### 6. 作業の学びをスキルに反映する

`skill-opportunity-review` → 提案の採用判断 → `shiranui-hanten` → 必要なら `shiranui-hansode`

1. 長い試行錯誤や既存スキルとの摩擦など、再利用する価値のある学びがあった場合に振り返ります。
2. 既存スキルの改善、新規スキル、文書・メモ、提案なしのどれが適切かを判断します。この段階ではファイルを変更しません。
3. 採用した提案がスキルの作成・更新なら、`shiranui-hanten` で要件から検証・配置まで進めます。
4. 指示の構造レビュー、変更前後の実行比較、反復調整を明示的に依頼した場合に `shiranui-hansode` を使います。

作るスキルがすでに決まっているなら、振り返りを挟まず `shiranui-hanten` から始めます。
単なる知識の整理は、必ずしも新しいスキルにする必要はありません。

## リポジトリの構成

| 配置先 | 内容 |
| --- | --- |
| [`dev/`](../dev/) | 開発作業の開始、設計、実装、検証、文書、引き継ぎを支援するスキル。 |
| [`meta/`](../meta/) | スキルの作成・評価・改善と、作業モードのスキル。 |
| [`knowledge/`](../knowledge/README.md) | スキル作成などで参照する、整理済みの再利用可能な知識。スキルの一覧とは別に管理します。 |
| `docs/` | このガイドなど、プロジェクトの説明文書。 |
| `.local/` | Git管理から除外する一時作業用の領域。公開・レビュー対象のファイルは置きません。 |

各スキルのフォルダには必須の `SKILL.md` があり、必要に応じて `README.md`、
`references/`、`scripts/` が含まれます。実行前に手順と同梱ファイルを確認し、
利用するプロジェクトのルールや権限に従ってください。
